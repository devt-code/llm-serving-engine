# Week 0: setup and baseline (2026-11-09)

## Environment
- Apple M3 Pro, 18 GB unified memory, macOS (Darwin 25.6)
- Python 3.11 (uv venv), torch 2.15.0, transformers 5.22.2, MPS available
- Qwen3-0.6B downloaded to `models/qwen3-0.6b` (1.5 GB bf16 safetensors)

## Model facts (config.json)
- 28 layers, hidden 1024, MLP 3072, vocab 151,936, tied embeddings
- 16 query heads / 8 KV heads (GQA 2:1), head_dim 128 (16*128 = 2048 != hidden 1024, so q_proj is 1024->2048)
- RoPE theta 1e6, RMSNorm eps 1e-6, plus per-head q_norm / k_norm (Qwen3-specific)
- KV cache per token: 2 * 28 * 8 * 128 * 2 B = 114,688 B, about 112 KB, so 4k tokens is about 459 MB

## HF transformers baseline (MPS, bf16, greedy, 128 new tokens, EOS ignored)
| batch | prefill (ms) | output tok/s | per-request tok/s |
|------:|-------------:|-------------:|------------------:|
| 1     | 40           | 59           | 60                |
| 8     | 133          | 260          | 33                |
| 32    | 436          | 530          | 17                |

Raw data: `bench/results/hf_baseline.json`. Reproduce: `python bench/hf_baseline.py --batch-sizes 1,8,32`.

Observations:
- Decode at bs=1 is memory-bound: about 60 tok/s, with the GPU idle most of the time.
- Batching to 32 gives about 9x total throughput, but per-request speed drops about 3.5x. That's the throughput/latency tradeoff the scheduler has to manage.
- HF static batching pads every prompt to the longest one, and the whole batch waits for the slowest request. Continuous batching (Phase 2) targets this.
